# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a professional, responsive Requester-facing ticketing experience for TokTickIT.
A Development Requester (a temporary testing identity, not real authentication) can
create an IT support ticket, attach supporting evidence, view and search their own
tickets in My Tickets, open a Ticket Detail screen, and manage their own attachments
through addition and soft removal — while the system guarantees that one Requester
can never see or modify another Requester's tickets.

## 2. Stakeholder Request Interpretation

The IT department needs a working Requester-facing intake flow before real
authentication exists. Since login is not available yet, the application must let a
tester pick one of several seeded "Development Requesters" to simulate being logged
in. Once a Requester is selected, they must be able to submit tickets with a category,
related system, priority, description, and optional file attachments; the system must
generate an official ticket number; and the Requester must be able to find, review, and
manage their own tickets and attachments — never anyone else's.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism only)
- Create Ticket screen and ticket creation API
- My Tickets screen: list, search, filter, sort, paginate
- Requester Ticket Detail screen (read-only ticket header)
- Attachment lifecycle: upload, list/preview metadata, download, soft removal
- Ownership enforcement (a Requester can only access their own tickets/attachments)
- Zen Green UI theme and reusable component conventions
- Unit, API, UI, responsive/visual, and E2E automated tests

### Excluded
- Authentication, sessions, passwords, tokens, real role-based authorization
- IT Staff dashboard, ticket claiming/reassignment, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Any ticket status change beyond the initial `New` status (resolve, close, reopen, cancel)
- Administrator functions (user/reference-data management)

## 4. Functional Requirements

- FR-01: The system shall provide a Development Requester Selection screen that
  lists only active Development Requesters loaded from PostgreSQL.
- FR-02: The system shall let the user select a Development Requester and store the
  selection as the current session's requester context.
- FR-03: The system shall let the user change the selected Development Requester at
  any time via a "Change Requester" action, reloading requester-specific data.
- FR-04: The system shall provide a Create Ticket form capturing Category, Related
  System, Ticket Summary, Requested Priority, Description, and optional Attachments.
- FR-05: The system shall generate a unique, backend-assigned Ticket Number upon
  successful ticket creation and display it to the user.
- FR-06: The system shall persist the created Ticket associated with the selected
  Requester's ID.
- FR-07: The system shall provide a My Tickets screen listing only tickets owned by
  the currently selected Requester.
- FR-08: The system shall support search by ticket number or summary on My Tickets.
- FR-09: The system shall support filtering My Tickets by Category, Requested
  Priority, IT Priority, and Current Status.
- FR-10: The system shall support sorting My Tickets by at least Created Date and
  Ticket Number.
- FR-11: The system shall paginate My Tickets results with a documented default and
  maximum page size.
- FR-12: The system shall provide a Requester Ticket Detail screen showing read-only
  ticket header information for one owned ticket.
- FR-13: The system shall reject any request for a Ticket or Attachment that does not
  belong to the currently selected Requester, without revealing whether the resource
  exists.
- FR-14: The system shall allow adding a new Attachment to an owned, existing Ticket,
  subject to type, size, and count limits.
- FR-15: The system shall allow downloading an active (non-removed) Attachment
  belonging to an owned Ticket.
- FR-16: The system shall allow soft-removing an owned Attachment, retaining its
  metadata but blocking further download or preview.
- FR-17: The system shall display appropriate loading, empty, no-results, validation,
  and failure states across all Lab 2 screens.

## 5. Business Rules

### Ticket defaults and system-generated values
- BR-01: The official Ticket Number is generated by the backend and must be
  globally unique (format: `TKT-YYYY-NNNNNN`, zero-padded sequential per year).
- BR-02: A new Ticket begins with Current Status `New`.
- BR-03: `createdAt` and `updatedAt` timestamps are system-generated; the Requester
  cannot set them.
- BR-04: IT Priority is not set at creation time; only Requested Priority is captured
  from the Requester in Lab 2.

### Requester selection and switching
- BR-05: Lab 2 uses a Development Requester selector instead of login. The selected
  identity is for testing only and is not authentication.
- BR-06: Only active Development Requesters appear in the selector; inactive
  Requesters are excluded from the dropdown entirely.
- BR-07: Changing the selected Requester immediately invalidates any previously
  loaded ticket data in the UI and reloads data scoped to the new Requester.
- BR-08: If no Development Requester is selected, any attempt to access My Tickets,
  Create Ticket, or Ticket Detail redirects to the Requester Selection screen.

### Ticket ownership
- BR-09: A Ticket belongs to exactly one Requester (`requesterId` foreign key,
  not nullable).
- BR-10: All ticket-read and ticket-write API operations must verify that
  `ticket.requesterId` matches the requester ID supplied in the request context;
  mismatches return a not-found-style response rather than a distinguishable
  "forbidden" response, to avoid leaking existence of another Requester's ticket.

### Search, filtering, sorting, and pagination
- BR-11: Search matches ticket number (exact or partial) or summary (case-insensitive
  partial match).
- BR-12: Filters (Category, Requested Priority, IT Priority, Current Status) are
  combinable (AND logic) with search.
- BR-13: Default sort is Created Date descending (newest first); Ticket Number
  descending is the secondary/tiebreaker sort.
- BR-14: Page size defaults to 10 and accepts values up to a maximum of 50; invalid
  or out-of-range page parameters fall back to the default rather than erroring.

### Validation and duplicate-submission prevention
- BR-15: Ticket Summary is required, trimmed, minimum 5 and maximum 150 characters. Frontend blocks submission client-side as a UX convenience when Summary is under 5 characters. The backend independently and authoritatively re-validates the same rule on every request and returns HTTP 400 if violated, regardless of what the frontend already checked — this covers direct API calls that bypass the UI.
- BR-16: Description is required, trimmed, minimum 10 and maximum 2000 characters.
- BR-17: Category and Related System must reference existing, active records; an
  invalid or inactive reference is rejected with a field-level validation error.
- BR-18: The Submit button is disabled and shows a busy state for the duration of the
  request to prevent duplicate ticket creation from repeated clicks.

### Failure behavior and data retained after errors
- BR-19: On validation failure, all previously entered field values (except file
  selections, per browser limitation) are preserved in the form.
- BR-20: On a backend/network failure during submission, the user sees a safe,
  non-technical error message and may retry without losing entered data.

### Attachment upload, download, and soft removal
- BR-21: Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF only; other
  types are rejected client-side and server-side.
- BR-22: Maximum attachment size is 5 MB per file; oversized files are rejected
  before upload completes.
- BR-23: A Ticket may have at most five active (non-removed) Attachments at a time;
  the six active attempt is rejected with a clear message.
- BR-24: Soft removal is required — a removed Attachment's file is not deleted from
  storage or the database; only a `removedAt`/`removedReason` marker is set.
- BR-25: A removed Attachment remains visible as metadata (filename, size, removal
  date) in the UI but cannot be downloaded or previewed.
- BR-26: Only the owning Requester may add or remove attachments on their own
  Ticket.
- BR-27: If Ticket creation succeeds but an attached file's upload fails, the Ticket
  is still saved; the user is informed which specific file(s) failed and may retry
  adding attachments afterward from Ticket Detail.

### Inactive Requesters
- BR-28: An inactive Development Requester cannot be selected, and any ticket data
  previously created under that Requester remains queryable only through direct
  database inspection, not through the Lab 2 UI/API surface.

### Empty and no-results states
- BR-29: My Tickets shows a distinct "no tickets yet" empty state when the Requester
  owns zero tickets, versus a "no results match your filters" state when filters/search
  produce zero results from a non-empty ticket set.

### Ticket Detail access
- BR-30: Ticket Detail is read-only for all header fields in Lab 2; only Attachment
  actions (add, download, soft-remove) are interactive.

### Transition to real authentication in Lab 3
- BR-31: The Development Requester selector and its associated session-context
  mechanism must be structured so that Lab 3 can replace it with real authentication
  without changing the Ticket/Attachment ownership data model.

## 6. UI Specification Summary

See `docs/lab-02/ui-spec.md` for the full specification. Summary:
- Application shell: TokTickIT header (Zen Green primary `#006B3C`), My Tickets and
  Create Ticket navigation, current Requester name display with Change Requester
  action, responsive mobile navigation (hamburger below 768px).
- Development Requester Selection: dropdown of active Requesters, Continue button,
  loading/empty/error states, explanatory text that this is a testing mechanism.
- Create Ticket: system-generated fields visually distinct (read-only shading) from
  editable fields; Summary/Description given generous width; Attachments section
  below main fields; busy-state Submit button; field-level validation messages.
- My Tickets: search bar, filter dropdowns, sortable columns (desktop table /
  mobile card list), pagination controls, Create Ticket action, loading/empty/
  no-results/failure states.
- Ticket Detail: read-only header grouped logically, separate Attachments section
  with active/removed/uploading states, download and soft-remove actions.
- Responsive breakpoints: Desktop >=992px, Tablet 768-991px, Mobile <768px per
  labsheet section 8.7.

## 7. Data Changes

New/updated Prisma models (see `server/prisma/schema.prisma` for authoritative
definitions):

- `RequesterUser` (temporary Lab 2 Development Requester): id, name, email
  (unique), isActive (boolean, default true), createdAt.
- `Ticket`: id, ticketNumber (unique, generated), requesterId (FK ->
  RequesterUser), categoryId (FK -> Category), relatedSystemId (FK ->
  RelatedSystem), summary, description, requestedPriority (enum: LOW, MEDIUM,
  HIGH), itPriority (nullable enum, unset in Lab 2), currentStatus (enum,
  default NEW), createdAt, updatedAt.
- `Attachment`: id, ticketId (FK -> Ticket), fileName, storedFileName,
  mimeType, sizeBytes, uploadedAt, removedAt (nullable), removedReason
  (nullable).
- `Category` (extended from Lab 1): unchanged shape, reused via relation.
- `RelatedSystem` (new): id, name (unique), isActive.

Indexes: unique index on `Ticket.ticketNumber`; index on `Ticket.requesterId`
(ownership lookups and My Tickets queries); index on `Attachment.ticketId`;
unique index on `RequesterUser.email`.

## 8. API Contract

See `docs/lab-02/api-spec.md` for full request/response shapes. Endpoint summary:

| Method | Path | Purpose |
|---|---|---|
| GET | /api/categories | List active Categories |
| GET | /api/related-systems | List active Related Systems |
| GET | /api/requesters | List active Development Requesters |
| POST | /api/tickets | Create a Ticket for the selected Requester |
| GET | /api/tickets | List the selected Requester's Tickets (search/filter/sort/page) |
| GET | /api/tickets/:id | Retrieve one owned Ticket |
| POST | /api/tickets/:id/attachments | Upload an Attachment to an owned Ticket |
| GET | /api/tickets/:id/attachments | List Attachment metadata for an owned Ticket |
| GET | /api/attachments/:id/download | Download an active, owned Attachment |
| DELETE | /api/attachments/:id | Soft-remove an owned Attachment |

All requester-scoped endpoints require a Development Requester ID, passed via the header `X-Requester-Id: <number>`, and enforce ownership server-side per BR-10.

## 9. Acceptance Criteria

- AC-01: Given valid Ticket data, when the Requester submits the form, then one
  Ticket is saved and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts to
  open My Tickets, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is
  requested, then the Ticket data is not returned.
- AC-04: Given a Ticket Summary shorter than 5 characters, when the Requester
  submits, then a field-level validation message appears and no API call is made.
- AC-05: Given a valid JPG under 5MB, when the Requester attaches it during
  creation, then it appears as an active Attachment on the created Ticket.
- AC-06: Given a 6MB PDF, when the Requester attempts to attach it, then the file
  is rejected with a clear size-limit message before upload.
- AC-07: Given a Ticket already has five active Attachments, when a sixth is
  attempted, then it is rejected with a clear message.
- AC-08: Given an owned Attachment, when the Requester soft-removes it with a
  reason, then it remains visible as metadata but its download link is disabled.
- AC-09: Given the Requester has zero Tickets, when My Tickets loads, then an
  empty state (not a no-results state) is shown.
- AC-10: Given filters that match no Tickets, when applied, then a no-results state
  distinct from the empty state is shown.
- AC-11: Given the backend is unavailable, when Create Ticket is submitted, then a
  safe error state is shown and all entered field values are preserved.
- AC-12: Given an inactive Development Requester, when the Requester Selection
  screen loads, then that Requester does not appear in the dropdown.
- AC-13: Given a Requester switches from Requester A to Requester B, when My
  Tickets reloads, then only Requester B's tickets are shown.
- AC-14: Given the desktop, tablet, and mobile viewports, when any Lab 2 screen is
  rendered, then no clipped labels, overlapping messages, or unintended horizontal
  scrolling occur.

## 11. Assumptions and Decisions

- Ticket Number format chosen as `TKT-YYYY-NNNNNN` for readability and year-scoped
  uniqueness; sequence resets are per-year, not per-Requester.
- Ownership checks return a not-found response (not a distinguishable 403) for
  cross-Requester access attempts, to avoid confirming that a ticket ID exists under
  another Requester (defense-in-depth, consistent with BR-10).
- Default page size of 10 chosen to balance readability on mobile card view with
  reasonable desktop table density; maximum capped at 50 to bound query cost.
- `itPriority` field is modeled now (nullable) even though IT Staff workflow is out
  of scope, to avoid a breaking schema change in a later lab.
